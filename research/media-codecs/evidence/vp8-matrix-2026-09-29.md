## Oracle methodology finding — suppressed-packet artifact

Discovered while investigating an apparent divergence after the first
invisible altref packet: **the divergence was in the ffmpeg-libvpx
reference, not zenvp8.**

- ffmpeg's libvpx decoder wrapper, fed a stream with `show_frame=0`
  packets, emits a *duplicate of the previous shown frame* in each
  suppressed packet's output slot. Output stays count-correct
  (N_packets − N_suppressed frames) but every frame after the first
  suppressed packet is shifted one slot — byte-diffs everywhere.
- ffmpeg's *native* vp8 decoder treats hidden frames as visible and
  emits them as output.
- Only a raw `vpx_codec_decode()`/`vpx_codec_get_frame()` loop
  (`tools/vp8-dec-raw.c`) reproduces libvpx's true emitted sequence.

zenvp8 output is byte-identical to raw-libvpx on the offending stream
(verified on `/tmp/vp8corpus/arf2.ivf`, 64 pkts / 4 suppressed / 60
shown — 1,105,920 bytes identical) and on the corpus `v0_arf2p` case.
`gen_vp8_cases.py` detects suppressed packets and selects the raw
decoder as canonical oracle automatically (`VP8_RAW_DEC` env var or
`tools/vp8-dec-raw`).

This is the same class of trap as the rusty_h264 frame-count semantics
findings: **a successful harness process is not codec qualification** —
the reference pipeline itself must be validated per-stream.

## Not covered / deferred

- Error concealment (libvpx `error_concealment.c`) — corrupt inputs
  return typed errors/corrupt-flagged output at libvpx's detection
  point; no concealment fill.
- SIMD — scalar reference-faithful code paths only.
- Realtime decode of large frames: ~1k fps @ 640×360 is
  correctness-first scalar; fine for qualification, not a perf claim.

# VP8/VP9 implementation audit and crate scoping — 2026-09-28

P3 of the media orchestration: find or scope a VP8/VP9 path. Verdicts below are
from executable probes (the shared harness + a 12-case libvpx-encoded corpus
cross-checked against ffmpeg's *native* vp9 decoder and libvpx itself), not doc
claims. Per-cell data: `vp9-matrix-2026-09-28.json`.

## `zenvpx` does not exist

No `zenvpx` repo under imazen. `imazen/zenmedia` carries AV1 (rav1d-safe decode,
zenrav1e encode) + IVF mux/demux + time/seek plumbing — no VPx work. The
decision is therefore "which existing implementation do we wrap", not "where is
our code".

### rusty_vp9 — primary VP9 decode candidate

Matrix vs ffmpeg-native-vp9 references (all inputs libvpx-vp9 encoded):

- **10/12 byte-exact**: p0_qcif/360p/720p/g12/rt/lossless, p1_422, p1_444,
  p2_10bit, trunc_tail. Covers profiles 0–2, 8/10-bit, 420/422/444, tiles,
  superframes (alt-ref invisible frames exercised by default libvpx encodes),
  and clean tail truncation.
- `corrupt_mid` = **concealment-divergent, not a failure**: libvpx rejected the
  corrupted packet at frame 15; rusty_vp9's first 5,184,000 output bytes are
  byte-identical to libvpx's, then it continued with its own error resilience
  to all 30 frames. ffmpeg-native's concealment diverged from both.
- `resize_concat` = **reinit_ok**: correctly emitted 12 frames @176x144 then 18
  @640x360 across the keyframe restart; the flat rawvideo reference cannot
  express per-frame geometry (same reference limitation as H.264 sps_switch).

Timing (median fps, release, x86_64): 354 @720p · ~1280 @360p ·
4,300–7,500 @qcif-class. Slower than libvpx single-thread per its README, but
far above realtime.

API fit for the bounded-session contract: `Vp9Decoder` is push/pull
(`push(packet, pts)` → `next_frame()` → `Again`/`Eof`), emits `DecodedFrame`
with tightly-packed planes + strides + `bit_depth` + `subsampling_x/y` + `pts`
pass-through — maps directly onto the session/frame-view contract without an
impedance layer. Zero dependencies. `Vp9Encoder`/`Vp9EncoderConfig` are also
public (K/P frames, GOLDEN+ALTREF groups, RC, two-pass, speed presets; README
states ~+36% bitrate vs libvpx at matched point — encoder needs its own
qualification round and is not on the first transcode path, which targets AV1).

Safety posture: **fails `forbid(unsafe_code)` on x86_64 (74 sites) and aarch64
(4); passes wasm32** — unsafe lives in inline AVX2/NEON paths, unlike
rusty_h264 whose accel code is feature-split into a separate crate (its
safe-core passes forbid on all three targets). If the media stack requires
forbid-clean video decode on x86_64, rusty_vp9 needs an upstream accel split
(feature-gate or `rusty_vp9-accel` crate) — the same shape rusty_h264 already
proved. Flag for Codex-side contract decision.

### wedeo-codec-vp9 — disqualified as a candidate

- License is **LGPL-2.1-or-later** (self-declared FFmpeg derived work). Cannot
  be relicensed; static-linking obligations make it incompatible with the
  Apache/MIT/commercial zen distribution model.
- Correctness: only 1/12 exact. Mismatches on clean streams (qcif 56k diff
  bytes, 360p 7.8M), `InvalidData` on the 720p tiled case, no output on 10-bit,
  broken chroma on 422/444 (emits luma-scale planes). It is a partial port.
- Retained value: **dev-time oracle** in this repo's research harness
  (`wedeo_vp9` adapter) for triangulating suspicious cells. Not shippable.

### zenwebp VP8 — not a video codec path

`vp8v2` rejects non-keyframes at `header.rs:38`; `encoder/vp8` emits WebP stills
only. Both are real, bit-exact-with-libwebp, zero-unsafe code — but VP8 *video*
(inter frames, golden/alt-ref state) is absent entirely. Extraction would also
pull a large internal subtree (bit_reader, loop_filter, dither, yuv, common
types, `#[arcane]`/zensim machinery). Not a viable zenvp8 seed without building
the entire inter-frame half.

**VP8 video decode has no qualified pure-Rust candidate.** It is the lowest-
priority codec here (legacy WebM input only; modern WebM is VP9/AV1). Options:
(a) defer, (b) `libvpx` FFI (C dep, breaks pure-Rust posture), (c) port FFmpeg's
native vp8 decoder (large). Recommend (a) + record the gap; revisit if
VP8-in-WebM input becomes a requirement.

## Scoping recommendation

1. **`zenvp9` = thin zencodec-media adapter over `rusty_vp9` (pin `=0.1.1`)** —
   decode side first. The push/pull + DecodedFrame shape already matches the
   session contract. Do NOT vendor/fork; consume crates.io release.
2. **VP9 encode**: rusty_vp9's encoder exists; defer qualification behind the
   AV1-first transcode route (VP9 output is not required by the plan).
3. **VP8**: defer; document gap. If needed later, libvpx FFI is the pragmatic
   path — but it reintroduces C deps the stack is designed to avoid.
4. **wedeo**: oracle-only. Do not ship. (Also LGPL: `wedeo-format-*` demuxers —
   mp4/webm/ivf — are equally off-limits as shipped deps.)
5. **Container note for P4**: the same `remade_ffmpeg_rs` monorepo publishes
   Apache-2.0 `rff-format-mkv` / `rff-format-ivf` / `rff-format-mp4` crates —
   candidate WebM/MP4 demux-mux building blocks worth auditing next phase.
